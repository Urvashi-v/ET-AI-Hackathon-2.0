# Data sources

What the system has ingested, where each piece came from, and how a viewer can
tell the difference on screen.

The short version: **the corpus running today is synthetic, labelled as such
everywhere, and generated deterministically from a written plant model.** The
requirement corpus is paraphrased rather than verbatim standard text. Nothing in
this repository fabricates a document and presents it as real.

---

## 1. The four provenance classes

Every displayable value carries a `data_class` from the database through the API
to a badge on the dashboard. It is never inferred client-side, and a value that
arrives without one renders as "Unlabelled" rather than quietly as real.

| Class | Meaning | Where it comes from |
|---|---|---|
| `real_source_document` | Extracted from a genuine ingested document | `data/corpus/` — ships empty |
| `synthetic_test_data` | Generated test data. Not a plant, not evidence | `data/synthetic/generated*` |
| `model_derived` | Produced by a model inference — never an audit record | embeddings, reranking, OCR, P&ID detection |
| `calculated_metric` | Deterministic computation over stored rows | asset stats, coverage figures, ROI outputs |
| `human_attested` | Confirmed by a named person — the only audit-grade class | feedback and corrections |
| `reference_taxonomy` | Curated vocabulary the system was configured with | equipment classes, failure modes |

The distinction is enforced, not decorative: a compliance response counts its
requirements by `text_status`, and the dashboard shows how much of any coverage
figure rests on paraphrase.

## 3. Synthetic corpus — `data/synthetic/`

Generated by `python data/synthetic/generate.py` (Markdown + CSV) and
`generate_pdfs.py` (real PDFs, including the image-only scan and the P&ID).
Full schema and plant model: **`data/synthetic/SCHEMA.md`**.

Three properties make it usable as an evaluation substrate rather than filler:

**It is scripted, not sampled.** Every work order, incident, inspection reading
and procedure step is written out explicitly in `generate.py`. The corpus has a
coherent causal story — a pump whose seal fails twice for a reason traceable
through an MOC to an impeller trim — rather than noise that happens to typecheck.
Clean random data makes a pipeline look good and then fails on the first real
document.

**Only the surface forms are randomised, and deterministically.** A seeded PRNG
chooses which of the six spellings of a tag a given document uses, whether a
failure code is meaningful or the dropdown default, whether a date is present.
That is where the messiness a real corpus has actually lives.

**The same seed produces byte-identical output.** `--seed` defaults to
`20260101`. This is verified in CI by generating twice and diffing. It matters
because document identity is a SHA-256 over file bytes: non-determinism here
means re-ingestion creates duplicates instead of converging. It has already
happened once — platform newline translation produced CRLF on Windows and LF in
the container, four near-duplicate documents, and a silent corruption of every
count. `.gitattributes` and an explicit `newline="\n"` now close that off.

**It is labelled in its own content.** Every generated file carries a
`SYNTHETIC TEST DATA` banner in the document text itself, so a screenshot of a
source page cannot be mistaken for a real one.

## 4. Real document corpus — `data/corpus/`

**Ships empty, deliberately.** `.gitignore` excludes its contents; only
`.gitkeep` files and documentation are committed. Most industrial documents are
either licensed or contain personal data, and inventing one to fill the gap
would be exactly the failure this project is built to avoid.

```
data/corpus/
├── pid/           Piping & instrumentation diagrams
├── work_orders/   CMMS exports (CSV) or individual work order PDFs
├── sops/          Standard operating procedures, operating instructions
├── inspections/   UT/RT/MPI reports, thickness surveys
└── incidents/     Incident and near-miss investigation reports
```

**`data/corpus/SOURCES.md` names where to obtain each class legally** —
university teaching materials and vendor documentation for P&IDs, public-sector
operators and OEM manuals for SOPs, and the licence caveat that applies to each.
`MANIFEST.schema.json` defines the metadata to record alongside anything added.

Dropping real documents in and re-running the ingest raises the ceiling on every
metric the evaluation harness reports. Synthetic-only data caps it, and the
README says so.

## 5. Requirement corpus — `data/requirements/`

20 atomised obligations across 8 instruments:

| Standard | Requirements |
|---|---|
| OISD-STD-105 (work permit system) | 6 |
| OISD-STD-128 | 3 |
| OISD-STD-130 | 3 |
| OISD-STD-145 | 1 |
| Factories Act 1948 | 3 |
| ISO 9001:2015 | 2 |
| ISO 45001:2018 | 1 |
| PESO SMPV Rules | 1 |

**All 20 are `text_status: paraphrase_for_demo`.** They are plain-English
restatements written for this project, based on the published *structure* of each
standard. The clause number identifies where such an obligation sits; the wording
is not the standard's, and nothing here reproduces the text of a paywalled
document.

This is enforced rather than noted: `requirements.text_status` is `NOT NULL`, the
compliance API returns `requirement_provenance` counting rows by status, and the
dashboard renders that count. A coverage figure built entirely on paraphrase is
visibly a coverage figure built entirely on paraphrase.

Each requirement also carries a **testability mode**, which decides what the
system is allowed to conclude:

| Mode | n | Machine verdict possible? |
|---|---|---|
| `evidence_document` | 8 | yes — is there a document of the required type in date? |
| `graph_state` | 4 | yes — does the graph hold the required relationship? |
| `procedure_text` | 5 | partial — text similarity flags a candidate; a human decides |
| `permit_record_field` | 3 | only where a permit record exists to read |

Requirements in the last two modes are reported as `not_evaluable` rather than
guessed at, and the reported coverage is explicitly
`coverage_pct_of_decidable`. **See `data/requirements/README.md` before adding
anything**, including the exact provenance note format for verbatim text.

## 6. P&ID training data — `data/pid_training/`

Symbol detection for equipment shapes (pumps, vessels, exchangers) is **not
implemented**, and the directory says what would be needed rather than shipping a
model with invented accuracy.

`dataset.yaml` defines the class list and directory structure a YOLO-format
detector would need; `README.md` states the annotation volume required and why no
accuracy figure is quoted. The tag, ISA bubble and pipe-run detection that *does*
run uses classical computer vision (pdfplumber word geometry, `cv2.HoughCircles`,
`cv2.HoughLinesP`) and needs no training data — see `docs/pid.md`.

## 7. What a viewer sees

| Surface | Where provenance appears |
|---|---|
| Every dashboard value | a `data_class` badge, with the meaning in its tooltip |
| Copilot citations | document title, page, and the verbatim span, clickable to the rendered source page |
| Compliance results | `requirement_provenance` counts by `text_status` |
| ROI model | every field tagged `USER INPUT`, `ASSUMPTION`, `MEASURED` or `CALCULATED` |
| Ingestion jobs | a per-stage report, including the stages that could not run |
